# O1: a learned judge over the 40-pool (2026-10-22, rerank.py, dial M40 off, no model written)

**The question.** The right skill is in the 40-pool 46 of 58 times but in the top 3 only 12-13 times. Can a judge
learned from what Claude really reached for (hindsight labels) order the pool better than the hand-tuned fusion?

**The setup.** Ten fair features per candidate (each reading's rank as 60/(60+rank), fused fit, tool, pin, task words
shared with the name, with the description, how many readings ranked it, pool position). Logistic regression, plain
SGD, positives up-weighted. Walk-forward: train on labelled prompts before a date, judge on the ones after it and on the
58 held-out probes the model never saw. McNemar on the paired top-3 vectors. The tool refuses `--write` unless every
unseen set rises.

| run | train | unseen set | top-3 base -> rerank | McNemar p | written? |
|---|---|---|---|---|---|
| split 2026-10-16, l2 0.01 | 50 prompts (18 with the answer in the pool) | test, 59 after the split | 7 -> 4 | 0.375 | no (falls) |
| same | | held-out 58 | 13 -> 17 | 0.344 | no (the test set fell) |
| split 2026-10-23, l2 0.1 | 109 prompts (45 in-pool) | held-out 58 | 13 -> 9 | 0.455 | no (falls) |

**What it says.** With 18 to 45 positive examples the judge cannot beat the fusion on unseen prompts. The one run that
rose on held-out (+4) fell on the time-forward test set (-3); neither move is distinguishable from noise. The learned
weights disagree between runs (r_raw -2.5 in one, shared_name +1.5 in the other), which is what overfitting to a few
dozen labels looks like.

**The honest reading of "does it get better than this?"** Not from more code. The judge is starved of labels, not of
features. Every lever that could move top-3 now runs through the label count:
- O2: more labels (ledger FIT works and owner ratings as labels; cloud ledgers merged);
- O3: a bigger probe set with a significance budget (58 is too few to tell +4 from luck);
- O9: the 12 pool misses are description problems, fixed at the source, which lifts the ceiling itself.
When the label count passes a few hundred with a hundred-plus in-pool positives, re-run `rerank train --split` and
let the McNemar line decide. Until then dial M40 stays off and the fused order stands.

**Receipts.** `maestro.py rerank train --split 2026-10-16`, `... --split 2026-10-23 --l2 0.1`; both RERANK rows are in
the ledger with the per-set counts and the verdict. `rerank status` says "no saved model".
